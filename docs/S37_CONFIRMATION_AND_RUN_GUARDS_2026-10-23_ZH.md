## 为什么能用这些资料，但还不能叫“临床验证通过”

新题是原创合成对话，没有使用真实病历、购买题目的原文或西安资料。本轮实际打开的资料包括 [NHS 鼻出血说明](https://www.nhs.uk/conditions/nosebleed/)、[NIDDK 胆结石治疗说明](https://www.niddk.nih.gov/health-information/digestive-diseases/gallstones/treatment)、[NHS 胆结石说明](https://www.nhs.uk/conditions/gallstones/)和 [NIDCD 突发听力下降说明](https://www.nidcd.nih.gov/health/sudden-deafness)。NICE 页面访问失败，没有拿它作为已核实的答案证据，也没有凭空套用全球统一的“24 小时转诊”规则。

这些资料能支持大方向，不能自动证明我们设定的半分边界、严重程度和中英文难度相同。中文对话按中文使用习惯独立组织；沿用结构里的 `machine_translation_unreviewed` 标记，是为了保留“尚未经过专业语言审核”的状态。具体问题已加入 H127，后期交审核者处理，不因此暂停合成题的工程开发。

程序检查了选定开发组与确认组是否共用规范化后的来源地址、是否落入已有的同机制分组。它不是完整的语义去重，更不能证明模型训练时没见过相关材料。本地调用记录的文件名筛查没有找到这些预留编号，但这也不能证明外部从未接触。确认题仍是公开草稿，不是保密测试集。

这十二份分轮输入只做结构检查：首轮不能看到下一轮的信息和标签。没有送给目标模型，也没有给参考答案打数值分。最终确认前必须锁定共用评分版本；确认结果无论通过、失败还是不确定，都结束本轮，不看了成绩再回头改题。

## 本轮发现的费用问题，比继续堆测试更值得先处理

S36 的数量设计没有改变：首阶段最多 816 次，后阶段最多 504 次，分别申请批准。此前写的 $55／$35／合计 $90 是拟议额度，不是已经获批或由程序保证的账单上限。

问题在于，S36 的一种费用情景把 8,192 输出 token 当作连推理过程一起封顶。[xAI 当前说明](https://docs.x.ai/developers/model-capabilities/text/best-practices)却明确指出，可见回答的长度限制不包含推理 token。因此，只在本地按可见长度扣预算，不能保证真实账单不超额；请求超时也不等于服务商已停止生成或计费。

[Google 的 Generate Content 思考说明](https://ai.google.dev/gemini-api/docs/generate-content/thinking.md)描述了包含思考的总输出限制，但项目现在用的是 [Interactions 接口](https://ai.google.dev/api/interactions-api)，不能未经核实就把另一接口的保证搬过来。[MiniMax 文档](https://platform.minimax.io/docs/api-reference/text-openai-api)说明了包含思考的生成长度限制；不过[现价概览](https://platform.minimax.io/docs/pricing/overview)没有把 M2.7 的现价问题交代清楚。之前成功调用过，只证明当时能用，不证明今天的价格。本轮没有认定任何一家 API 故障，也没有删掉 MiniMax。

输入 token 同样需要可靠上界，不能拿“字符数除以四”当硬保证。未知的计费长度或价格必须使真实调用停在发送之前，不能悄悄套用平均值。

## 代码现在保护了哪些环节

[运行保护模块](../benchmark/run_guard_s37.py)已加入各服务商的候选请求草稿、用十进制向上取整的预算预留，以及本地模拟调用日志。模拟发送前先写尝试记录和请求，解析前先保存原始回复字节。无效 JSON、HTTP 错误、返回了别的型号、校验拒绝或中断，都保留，不靠重试或修补把它们藏起来。失败或送达不明的尝试不退回预留额度；合法的 `unclear` 则是结果，不是重新抽一次的理由。

新目录权限为 0700，文件为 0600，采用独占创建和落盘同步；不覆盖旧运行，不支持继续一个中断的运行，也不把异常消息里的潜在敏感内容写入元数据。这个版本只接收模拟字节或异常，不加载密钥、不发 HTTP。即使把配置中的“准备好了”改成真，真实调用检查仍关闭。请求里的 `store=false` 也不等于我们已证明服务商完全不留存。

**仍未完成**的是完整真实调用调度、实际 HTTP 原文保存、逐请求计费上界、用量对账、有效采样参数冻结，以及与明确批准绑定的协议指纹。[离线快照](../config/s37_offline_frozen_v1.json)只锁定已经完成的题目、预留和保护组件，不冒充完整跑分方案。S26–S36 历史文件和成绩保持不变。

## 接下来按什么顺序做

1. 先解决费用约束，暂不申请“批准 $55 就能安全跑完”。优先核实包含全部计费 token 的上界；若做不到，再与项目负责人选择专用的服务商侧预算方案或明确改订费用政策。[xAI 的账单说明](https://docs.x.ai/console/billing)描述了预付余额用尽、账期额度为零时拒绝后续请求的机制，但现有余额、自动充值、其他程序共用及在途消耗都要核实。本轮没有查看或更改账户设置。
2. 补齐 M2.7 现价与各接口参数证据，完成真实调度器和模拟全流程／关口测试。Gemini、Grok、MiniMax 各两款的名单保留。
3. 冻结完整新协议后，再申请明确的材料发送、调用次数和费用批准。先做控制题，再做开发组；最多一次事先规定的工程修订，最后另批确认组。当前真实调用额度仍是 **零**。

均分目标继续是**固定较广模型组整体约 80**，两名裁判分别报告，不是让每款模型都考 80。不能调曲线、放松安全或看了结果再挑模型来凑分。专家审核仍是后期认证／发布关口；当前真实运行未启动的原因是费用和工程准备，而不是要求先找医生签字。

离线复查命令：`python3 -m benchmark.confirmation_s37`；全量测试：`python3 -m unittest discover -s tests -q`。另见[审计摘要](../data/audit/s37_confirmation_summary.json)与[未完成事项](../config/run_s37_readiness_v1.json)。
