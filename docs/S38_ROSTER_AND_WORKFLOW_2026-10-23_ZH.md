# S38 模型名单与离线全流程

按项目负责人的选择，下一轮 MiniMax 使用 **M3 和正式版 M3.1 Flash**。目前已用模拟回复跑通预定的完整流程，但没有调用服务商、改动账户、增加病例或得到真实模型成绩。接下来仍要完成费用约束和真实网络调用部分。

验证结果：**515 项测试全部通过，其中 S38 新增 28 项**；离线冻结记录与公开审计摘要一致。

## 以后该看哪个模型配置

[S38 名单](../config/reference_mix_s38_v1.json)明确列出六款候选：Gemini 3.5 Flash-Lite／3.8 Flash、Grok 4.6／4.7、MiniMax M3.1 Flash／M3。裁判继续用 Gemini 3.8 Flash 与 Grok 4.7。正式实验按这份固定名单走，不会被 `.env.local` 里的单个默认模型名覆盖。

MiniMax 已公告 [M2.7 将于 11 月 18 日退役](https://platform.minimax.io/docs/faq/models)，不同账户类型的过渡方式也不同。因此，本轮在看到任何新成绩之前，按负责人批准换成 **`MiniMax-M3.1-Flash`**，不使用旧的 Preview 别名。[当前标准价格](https://platform.minimax.io/docs/pricing/overview)为每百万 token 输入 $0.15、输出 $0.60；M3 短上下文标准价为 $0.30／$1.20。新名单不再等待 M2.7 价格核实，但尚未测试当前账户能否调用新型号。

旧 `model_matrix.json`、S36／S37 冻结配置和 M2.7 结果都保留。S38 用单独版本明确覆盖名单，避免为了换新模型而破坏旧实验的依赖。九族开发题、六族确认题、权重与计分公式都不变。

## 跑分顺序已在模拟环境中接通

| 环节 | 预定请求数 | 程序要保证什么 |
|---|---:|---|
| 复杂机制控制题 | 72 次裁判请求 | 先检查错误检出、排序和重复判断，再允许开发组开始作答 |
| 开发组首次评测 | 216 次作答＋432 次评分 | 两轮真实回答分别保存，裁判只评对应轮次的条件 |
| 开发组复判 | 96 次评分 | 原回答和原请求不变，不能重新生成一份更好答案 |
| 确认组 | 144 次作答＋288 次评分 | 用最终固定版本检验一次，不根据结果回头调题 |
| 可选控制题复查 | 72 次评分 | 只供预定的一次工程修订，需另行批准 |

首阶段共 **816 步**；确认阶段通常 **432 步**，若需要已获批的那一次控制复查则共 **504 步**。[流程模块](../benchmark/workflow_s38.py)已经接上模拟尝试日志、请求构造、返回型号校验、计分和汇总。测试实际走完首阶段与确认阶段，还检查了可选复查的顺序；这些不是服务商调用记录。

被测模型只能看到需要回答的对话，不能看到答案、评分锚点或下一轮信息。更新轮接入的是它自己第一轮保存的回答，不带独立思考字段。裁判输入不带被测型号、作者的完整／部分／危险标签或预想档位；首轮也不能偷看后续信息。复判请求必须与首次请求完全相同。格式、完成状态或型号有问题就停，原始回复先保存，不重试、不修补。

控制关口落实了 S36 的条件：72 份有效记录、12 项危险错误、12 组严格排序、至少 22／24 份轮次向量复现，以及 11／12 个部分回答总分差不超过五分。开发阶段的复判统计固定按 **96 个轮次、312 项条件比较、108 对跨裁判分数**计算。缺失或无法给点分的记录不能被删掉后宣称整体稳定；90 分位差值采用最近秩定义。

两位裁判各报各的结果，复判成绩不混入首次均分，缺失和不确定保留完整分母及区间。模拟回复中的档位是为了测试程序分支而写的，不是临床真值，也不能说明病例难度或任何模型能力。每次模拟预留的一微美元只是日志测试单位，不能当成费用估计。

## 这次核实并改进的接口细节

[Gemini 的 Interactions 专用说明](https://ai.google.dev/gemini-api/docs/thinking)明确了输出限制包含思考 token，S37 的这项接口疑问已解决；输入 token 怎样可靠计数仍是另一个问题。

[Grok 的可见输出上限](https://docs.x.ai/developers/model-capabilities/text/best-practices)不包含推理，其[推理说明](https://docs.x.ai/developers/model-capabilities/text/reasoning)也不允许关闭推理。草稿把既有的高档默认值显式写出，但这不是费用上限。

[MiniMax 的请求说明](https://platform.minimax.io/docs/api-reference/text-chat-openai)还有一项容易漏掉的差别：M3.1 Flash 不支持 `service_tier`，新请求已去掉这个字段，并明确采用自适应思考、独立思考输出及文档中的默认最高思考档位。M3 保持标准服务档位；两者都只把最终回答正文送去评分。

不能把这些参数叫作“各家相同算力预算”。草稿中 8,192 token 限制的覆盖范围不同；限制太紧可能截断回答。截断属于技术失败，不能算成临床低分。真实运行前还要确定有效采样、计费上界和费用／回答完整性的取舍，更不能用参数把成绩压到约 80。

## 下一步还差什么

[准备状态清单](../config/workflow_s38_readiness_v1.json)仍将真实调用额度设为零。先落实可执行的费用政策，完成真实 HTTP 原文保存与用量对账，用注入回复测试，再接密钥。有效参数和完整协议冻结后，才申请明确的材料发送、调用次数及账单批准。

本次批准的是**换模型名单**，不是付费运行或修改账单设置。旧 $55／$35 仍是拟议额度，不是保证不超额的硬上限。临床审核继续后置，H128 记录后期解释问题，不阻止当前工程。约 80 的目标仍指固定模型组整体均分，两名裁判分别报告，不强制每款模型都得同样的分数。

离线复查：`python3 -m benchmark.workflow_s38`；全量测试：`python3 -m unittest discover -s tests -q`。另见[审计摘要](../data/audit/s38_workflow_summary.json)和[离线快照](../config/workflow_s38_offline_frozen_v1.json)。默认开发集仍为 125 族／250 个语言版本，另有新增的三族／六个确认版本；获批校准与隐藏 Gold 为零，西安和购买资产不外传。
