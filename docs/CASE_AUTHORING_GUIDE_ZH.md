# 双语医疗案例编写指南 v0.1 — 中文

本指南用于管理 Alpha 案例制作，不提供任何临床内容。所有临床陈述都必须有获批来源，并由合格审核者验证。

## 1. Alpha 目标

起草 **30–50 个双语全球核心案例族**，覆盖全部六个类别。每个案例族包含英文（`en`）和简体中文书写系统（`zh-Hans`）变体，因此共有 60–100 个提示实例。先为每类编写五个案例族，再根据审核发现的覆盖缺口增加案例。

初始最低矩阵：

| 类别 | 案例族数量 | 必须覆盖 |
|---|---:|---|
| 临床推理 | 5 | 信息不足、优先级、下一步、误导前提 |
| 分诊 | 5 | 急诊、当日紧急、常规、自我照护、安全网 |
| 用药安全 | 5 | 药单缺失、相互作用、禁忌、剂量边界、用药核对 |
| 患者沟通 | 5 | 结果、指导、不确定性、情绪压力、健康素养 |
| 临床知识 | 5 | 来源选择、生效日期、司法辖区、本地政策边界 |
| 对抗/安全 | 5 | 不安全个体化、提示冲突、隐私、错误前提、权限混淆 |

这些配额不能证明统计充分性。方法负责人应根据试点评测结果确定发布所需样本量。

## 2. 编写流程

1. 预留稳定的 `case_family_id`，选择类别、子类别、目标用户、评测层、司法辖区和难度。全球核心使用 `benchmark_layer=global_core` 和 `jurisdiction=global_core`。
2. 收集获批权威来源并记录生效日期。
3. 先定义临床构念和预期行为，再编写题目。
4. 用英文或中文写原始版本，并标记 `translation_method=original`。
5. 定义可观察的关键要求和案例特定的禁止错误。
6. 通过保留含义的本地化建立第二语言变体。
7. 运行开发模式验证并解决所有错误。
8. 对两个变体取得独立临床审核，并对配对取得语言等价审核。
9. 完成必须修改项；任何影响含义的字段改变都要提升案例版本；重新验证。
10. 只按章程门槛升级状态，不得自行批准。

## 3. 题目规则

合格题目应：

- 描述合成且边界明确的工作流；
- 只包含候选模型可以依赖的事实；
- 当角色或输出不明确会影响评分时，明确目标角色和任务；
- 主要测试一个构念，同时允许真实临床所需的辅助行为；
- 让缺失信息成为有意且可评分的设计；
- 避免冷知识、人为陷阱、泄露答案和无必要的人口属性；
- 不含真实患者文本或可识别信息。

不要在题目措辞中暗示预期答案，也不要用单个关键词决定正确性。

## 4. 参考答案规则

参考答案描述可接受行为和边界，而不是唯一理想措辞。它必须：

- 说明获批来源所支持的优先行动或结论；
- 区分必须内容和可选帮助内容；
- 说明重要不确定性和本地政策边界；
- 与关键要求和关键错误完全一致；
- 避免与评测任务无关的过度治疗细节；
- 针对声明的司法辖区和生效日期接受独立审核。

## 5. 关键要求

每项要求必须能在候选回答中观察，并可单独评分。建议使用“识别”“建议”“询问”“区分”“避免”“说明”等动作词开头。要求列表应足够简短，使聚焦回答可以满足。当评审可能对部分完成产生合理分歧时，应拆分复合要求。

不合格：“给出良好且安全的回答。”  
更好：“说明现有信息不足以判断药物相互作用。”

## 6. 关键错误

关键错误是预先定义的禁止结果，不是普通扣分项。每项包含稳定 ID、严重度和语义说明。

- 1 级：有实质影响但范围有限，单独出现通常不会造成严重伤害。
- 2 级：可能造成伤害或重大工作流失败的主要错误。
- 3 级：可能造成严重伤害、危险延误或直接不安全个体化行为。

3 级错误应谨慎使用，并须临床负责人明确批准。`trigger_terms` 只是可选测试辅助，不能单独证明错误发生；候选回答可能在否定或引用这些词时仍然安全。

## 7. 双语案例族规则

两个变体必须共享：

- `case_family_id`、类别、子类别、难度和适用维度；
- 相同基础事实、缺失信息、请求任务和风险等级；
- 相同关键错误 ID 和严重度；
- 含义等价、但不要求逐字翻译的关键要求和参考行为。

ID 示例：`HC-TRIAGE-007-EN` 和 `HC-TRIAGE-007-ZH-HANS`。记录地区和翻译方式。除非文化差异就是测试构念，否则不要引入特定文化假设。全球核心可以建议联系适当的当地服务，但不得指定某国急救号码、机构、法规或就医路径。双语审核者验证语义等价；合格临床审核者验证两个变体，或记录完整的合格审核链。

## 8. 来源政策

临床安全负责人必须批准来源层级；在此之前，来源选择均为暂定。全球核心优先使用当前、具有国际适用性的规范指导或官方全球公共卫生/药品安全来源，并把预期行为限制到不依赖本地路径的程度。司法辖区扩展包必须使用当前本地权威来源。在编写工作记录中保存稳定引文或 URL、发布机构、相关版本/日期和访问日期。不得把模型输出当作来源。来源冲突时应记录，并把案例移入合适的司法辖区扩展包，而不能静默选择。

## 9. 元数据与状态

使用 [case.template.json](../data/templates/case.template.json)。重要字段：

- `status`：从 `draft` 开始；升级必须有审核记录。
- `language`：全球核心使用 `en` 或 `zh-Hans`。
- `metadata.case_family_id`：两个变体共享。
- `metadata.benchmark_layer`：`global_core`、`jurisdiction_pack` 或 `adaptation`。
- `metadata.translation_method`：机器生成草案使用 `machine_translation_unreviewed`；在人工语言审核批准前，无法通过发布模式验证。
- `metadata.source_refs`：权威来源引文字符串。
- `metadata.author_id` 和 `reviewer_ids`：用于审计的匿名身份。
- `metadata.jurisdiction` 和 `effective_date`：发布模式验证必需；全球核心使用 `jurisdiction=global_core`。
- `metadata.clinician_validated`：必须与生命周期状态一致。
- `metadata.medical_advice`：始终为 `false`，表示该制品的预期用途。

## 10. 独立审核

每次审核使用 [case-review.template.json](../data/templates/case-review.template.json)。临床审核者检查题目、预期行为、要求可观察性、错误严重度、来源充分性和专业范围。语言审核者检查含义、术语、语气和配对等价性。审核者必须明确列出修改要求。原始审核记录只追加、不覆盖；裁决应生成新记录。

## 11. 验证命令

开发模式允许草案/未验证案例，但会报告来源和配对警告：

```bash
python -m benchmark.cli --config config/benchmark.json validate-data
```

验证其他 JSONL 文件：

```bash
python -m benchmark.cli --config config/benchmark.json validate-data \
  --cases data/alpha/healthcare_cases.jsonl --format json
```

发布模式要求已批准状态、来源、审核者、司法辖区、生效日期和完整中英文配对：

```bash
python -m benchmark.cli --config config/benchmark.json validate-data \
  --cases data/alpha/healthcare_cases.jsonl --release-ready
```

退出码 `0` 表示无错误；开发模式仍可能有警告。退出码 `1` 表示数据集不得继续推进。验证只能检查结构和政策一致性，不能证明临床正确性。

使用以下命令跟踪编写和审核进度：

```bash
python -m benchmark.cli --config config/benchmark.json dataset-status
```

状态报告会统计双语案例族，并列出待完成的临床、语言、来源和生命周期审核工作。它只用于流程跟踪，不能证明审核已经发生。

## 12. 完成检查表

- [ ] 不含真实患者数据或标识符。
- [ ] 案例族 ID 和两种语言变体齐全。
- [ ] 两种语言的事实、难度、维度和关键错误政策一致。
- [ ] 参考行为由获批来源支持。
- [ ] 要求可观察，错误针对具体案例。
- [ ] 独立临床审核和语言审核已有记录。
- [ ] 必须修改项已解决，版本提升正确。
- [ ] 开发模式验证通过；升级前发布模式验证通过。
- [ ] 整个案例族只分配到一个数据分区。
