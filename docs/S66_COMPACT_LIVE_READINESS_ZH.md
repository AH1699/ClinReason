## 这次具体往前走了哪一步

上一轮 S65 把评审模型要处理的引用格式缩小了，并定好一批最多 16 次请求的检查。本轮补齐了真正发请求之前的授权、留档和事后核对能力。[执行程序](../scripts/compact_live_s66.py)、[固定范围](../config/compact_live_s66_v1.json)和[冻结清单](../config/compact_live_s66_frozen_v1.json)已经独立建立；[S65 方案](S65_COMPACT_FEASIBILITY_ZH.md)和旧 S62 结果不回改。

简单说，程序现在会先确认“这份批准是否对应这套材料、是否过期、是否用过”，再读密钥。每次联网前先登记这一笔；拿到回复后，先保存原始内容和费用依据，再检查答案能不能用。事后可以只读本地记录，从原始回复重新还原判断，不靠相信先前保存的“成功”标志。

若运行中断，不自动重发；无法确定是否送达或费用多少，就保留未知状态并停止。已知费用但评审格式不合格，只关闭评审通道，独立的 MiniMax 检查还能继续；若某个 MiniMax 回答不完整，只关闭该型号剩余回合。金额达到停止线、资料被改动或出现费用／送达不明，则全部停止。

离线测试还发现一个容易忽略的问题：保存 JSON 时调整字段顺序，会改变实际放进提示词的那段文字。现在同时保留并绑定原有序列化顺序，保证重放出来的请求与 S65 冻结请求完全一致；并没有为此改标签、提示词内容或评分公式。

这些保护针对可信的本地操作者，防止误操作和记录不一致。授权文件只是对真实用户同意的留档，不是能对抗恶意电脑操作者的身份认证；本地哈希也不能独立证明回复确实来自服务商。

## 需要确认的费用规则

建议批准这一批最多 16 次请求，**累计记录费用达到 3 美元后停止，但最后一笔可能使总额超过 3 美元**。这不是账户硬限额。费用未知时不继续发，也不把未知当成免费。

按每次输入不超过 16,000 token、计费输出不超过 32,768 token 的规划假设，估算约 1.80 美元；这既不是实际测出的 token 总数，也不是账单上限。字节数少不等于 token 一定符合假设。如果实际输入超过当前 16,000 token 的核算范围，就按费用未核清停止。记录中的 token 估算不能冒充服务商账单。

## 已验证什么，还没验证什么

另有一轮使用真正冻结的六份来源题包的完整离线演练：[公开核对记录](../data/audit/s66_compact_live_rehearsal.json)显示 16 次模拟请求均可由原始记录还原，包括十二份评审、六组重复判断和四个作答回合。0.027810 美元只是模拟用量产生的数字，实际没有花费，也不预测真实费用。公开文件只放摘要、哈希及状态，不放原始回答、推理或授权内容。

即便这些技术条件都通过，程序也**不会自动宣布小批实测通过**。真正拿到模型回复后，还要在本地逐项查看引用是否确实支持该要求，有没有引得太宽、漏掉限制条件，以及允许空引用的项目是否合理。能从原文找回文字，不等于那段文字具有临床支持力。[H155 与临床待审清单](CLINICAL_REVIEW_HANDOFF_ZH.md)继续保留；本地初审不替代专家审核。

## 本地怎么用

`proposal` 只展示待批范围，不读密钥；`rehearse` 只跑模拟连接；`replay` 只读已存记录，不会续跑。它们都属于 `python3 -m scripts.compact_live_s66` 的子命令。

只有取得明确的新批准后，才把真实同意内容、批准人、批准及到期时间、协议哈希和唯一的批准／运行编号记入被忽略的私有 `work/s66-approvals/`。还须明确接受收费、资料发送范围、末笔超额、不重试／续跑、失败处理和结果仅作开发参考。先 `preflight` 核对，再用单独的 `run` 入口执行一次；程序不会自行生成批准。不得把单元测试里的虚构授权复制进去作为消费凭据。
