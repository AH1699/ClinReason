# S34 本轮加入 MiniMax 的流程检查

## 本轮怎样加入 MiniMax

用户已同意继续 S33，并明确要求这次也测试 MiniMax。S33 原定的 **48 次裁判调用不变**；另外安排一个独立的 MiniMax 流程检查，最多 **24 次**，两部分合计上限 **72 次请求**。这个上限不代表金额封顶。

MiniMax `MiniMax-M2.7` 负责回答，Gemini `gemini-3.8-flash` 和 Grok `grok-4.7` 负责评分。选 M2.7 是延续此前成功生成过答案的配置，不代表已经确认今天的接口状态，也不代表预先认定它属于哪个能力档位。若返回模型名不符或调用失败，不自动换型号补跑。

这部分先验证“生成回答—分轮评审—算分”能否完整走通，不是 S33 通过后才能设计的广泛模型比较。两部分分别记录、分别计数、分别按规则停止；一边失败，不给另一边追加额度或改变规则。即使 MiniMax 流程全部完成，`comparison_ready` 和 `calibration_complete` 仍为 false；不能拿它来补救未通过的 S33 条件，更不能据此排名。

## 四段对话最多 24 次

沿用红眼 `TRIAGE-018` 和鼻窦 `TRIAGE-020` 两族题的原始中英文用户问题，共四段对话。每段先让 MiniMax 回答首轮，保存并校验后才给第二轮问题；再分别让 Gemini、Grok 评首轮和更新轮。

每段两次生成、四次评审，共六次；四段合计 **8 次 MiniMax 生成 + 16 次裁判评审 = 最多 24 次**，不复判。全部完成时有八份“对话—裁判”分数，但仍只有四段 MiniMax 对话，不能当作八个独立病例。

MiniMax 只看到候选模型说明、当前可见的合成用户信息和它自己的上一轮回答，看不到参考答案、评分标签、作者样例类别或目标分数。首轮裁判看不到后续病情；更新轮裁判可看完整对话，但只评更新轮要求。程序不额外把候选模型名称交给裁判；Google、xAI 会收到含 MiniMax 回答文字的合成对话、草案标签和评审说明。**不发送西安病历或采购原始资料。**

MiniMax 现有请求没有可用的禁止存储设置，不能承诺服务商零留存。Google／xAI 请求继续使用已有的 `store: false`，也不把它解释成对服务商所有留存行为的保证。

MiniMax 保留 `reasoning_split: true` 和 8,192 的补全 token 上限。后续对话和裁判只使用回答 `content`，不使用单独的思考字段；若回答正文仍混有 `<think>`、被截断、为空、服务商状态非成功或返回模型不符，则拒绝继续。原始回复可能含独立思考内容，只保存在被 Git 忽略的本地 `work/` 中。

## 怎样固定规则和核查结果

[配置](../config/minimax_s34_v1.json)、[冻结清单](../config/minimax_s34_frozen_v1.json)、[程序](../benchmark/minimax_s34.py)和[测试](../tests/test_minimax_s34.py)固定案例、候选提示词、接口适配器及 S33 评分依赖。指纹为：

```text
b74231a5ddfa9d07853456ef615693ac8a609cc809dc0af69a6bb9d3052e982a
```

真实回答尚未生成，无法预先固定它们进入裁判请求后的内容哈希。因此每次请求前，先记录当次实际输入的哈希。离线核查再从冻结问题和已验证的原始 MiniMax 回复重建请求，核对文字、模型身份、轮次和哈希；总分从两轮判断重新计算，不直接相信缓存结果。

评分沿用 S33 的提示词、边界、引用校验和算式。**MiniMax 没有预设分数，不要求拿 80，也不套用作者控制回答的预想档位。**有不确定项就保留区间，不强行给单一分数或通过结论。两位裁判的结果分别报告，分歧和缺失都保留，不计划计算排名平均分。

顺序固定为每个案例：MiniMax 首轮、更新轮；Gemini／Grok 首轮评审；Gemini／Grok 更新轮评审。每次请求的超时为 240 秒，采样用服务商默认值，不固定种子，不自动重试。首次传输或校验失败即停止这部分，不补跑、不续跑、不更换型号、不修复无效回复，也不混入以前 MiniMax 的结果。
