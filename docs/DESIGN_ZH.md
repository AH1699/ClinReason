# 医疗/诊所大模型评测基准设计 v0.1

状态：规划与技术脚手架，尚未完成临床验证  
读者：产品、评测、工程、临床安全与治理团队  
路线：先使用前沿大模型作为评审，再采用混合评审，条件成熟后才考虑蒸馏/训练开源评测模型

## 1. 核心决策

第一阶段应构建一个规模较小但质量高的基准，由两个不同模型家族或供应商的前沿模型独立评分，并加入抽样人工复核。当前最稀缺的资源不是推理算力，而是可信的领域判断。早期迭代应优先改进案例、评分锚点和裁决流程。

当人工标注的 Gold Set（黄金标准集）稳定后，可将低风险、高一致性的样本交给廉价评测模型；高风险、低置信度或存在争议的样本继续交给前沿评审模型和领域专家。只有当评测量、隐私、本地部署、可复现性或单位经济性能够覆盖训练与维护成本时，才考虑蒸馏开源评测模型。

v0.1 将以下部分解耦：

1. 行业通用评测引擎；
2. 医疗领域案例与关键错误政策；
3. 候选模型适配器；
4. 评审模型适配器；
5. 不可变的运行与版本元数据；
6. 人工复核与裁决。

因此，未来扩展到金融或法律时，主要新增领域内容和政策，而不必重写系统。

## 2. 目标与非目标

### 目标

- 衡量模型在诊所工作流中的回答是否正确、安全、合理分诊、完整、相关、易懂且能正确表达不确定性。
- 发现医学选择题难以暴露的失效模式，例如危险延误、无依据的个性化建议、捏造机构政策以及过度自信。
- 在明确记录的条件下复现不同模型及版本的比较。
- 逐步积累可用于校准分流策略或训练小型评测模型的高质量标签。

### v0.1 非目标

- 临床部署、监管认证或安全性证明。
- 自动诊断或治疗建议。
- 声称模型具备普遍的临床能力。
- 训练候选模型或评测模型。
- 使用真实 PHI/PII。
- 在完成临床验证、污染检查和统计分析前发布排行榜。

## 3. 预期用途声明

本基准用于评估文本模型在模拟医疗/诊所工作流中的行为，适用于研究、质量保证与模型选择。它不是临床决策支持系统，示例内容也不构成医疗建议。通过本基准不等于获得临床安全性、监管合规性或具体用途适用性的证明。

每个发布版本必须说明适用司法辖区、目标用户、支持语言、被测模型快照、已知排除项、验证状态以及参考指南的生效日期。

## 4. 基本原则

- **安全高于表达。** 即使文字流畅，只要给出危险处置建议就应失败。
- **案例要求必须可观察。** 评审依据明确要求和禁止错误，而不是主观印象。
- **不奖励冗长。** 完整性指覆盖必要信息，而非越长越好。
- **区分模型问题与案例问题。** 含糊、过时或有争议的案例可在裁决时隔离或移除。
- **全面版本化。** 案例、数据集、rubric、提示词、模型、参数、代码和参考指南都要独立标识。
- **明确人工责任。** 自动评审只能分配复核精力，不能替代临床正确性认证。
- **报告不确定性。** 发布置信区间和覆盖率，而不是只给一个排行榜分数。

## 5. 基准组成

MVP 目标为 300–500 个案例，建议初始配比如下：

| 类别 | 建议占比 | 核心能力 |
|---|---:|---|
| 临床推理 | 20% | 收集证据、排序可能解释、选择安全下一步 |
| 分诊与升级处理 | 20% | 判断紧急程度、去向、时间和安全网建议 |
| 用药安全 | 15% | 相互作用、禁忌、缺失信息和剂量边界 |
| 患者沟通 | 15% | 通俗解释、同理心、理解确认、可执行建议 |
| 临床知识 | 15% | 基于指南的知识，并识别司法辖区和时效性 |
| 对抗与安全 | 15% | 冲突指令、不安全请求、错误前提、提示注入 |

每类应平衡难度、就诊场景、任务形式、人口背景、语言、答案长度，以及“拒答/澄清是否为正确行为”。建议约 80% 为开放式场景，20% 为客观或结构化题。隐藏 Gold Set 应提高高风险和边界案例的占比。

## 6. 系统架构

```text
版本化案例 -> 候选模型适配器 -> 保存回答
                                    -> 评审 A --\
                                    -> 评审 B ----> 聚合/门控 -> 报告
                                    -> 成对比较 --/
                                             |
                                    复核触发 -> 专家裁决
                                             |
                                         锁定 Gold Set
```

MVP 使用 SQLite 即可。规范化标识符并保存 JSON 负载，方便 schema 演进。生产环境中的原始供应商输出应放在访问受控的对象存储中；本脚手架只保存解析后的内容。批处理平台、仪表盘和分布式队列不属于 v0.1 范围。

### 供应商抽象

候选模型适配器接收案例，返回文本以及可选的 token、延迟元数据。评审适配器接收案例、候选回答和 rubric，返回满足 schema 的结构化评分。成对比较为可选能力。认证、请求格式、重试、限流和结构化输出修复均封装在适配器内部。

## 7. 评测流程

1. 验证并冻结案例版本。
2. 创建运行清单，记录模型、提示词、参数和代码版本。
3. 使用相同案例呈现方式和受控解码参数生成候选回答。
4. 在技术允许时向评审隐藏候选模型身份。
5. 使用两个不同家族或供应商的前沿模型独立进行绝对评分。
6. 每个维度取中位数；对不适用维度剔除后重新归一化权重。
7. 在原始分数之后执行关键错误门控。
8. 计算置信度和人工复核触发条件。
9. 将分歧、硬失败、低置信度样本和随机审计样本交给合格专家。
10. 将裁决后的标签与开发数据分离并锁定。
11. 除总分外，同时报告类别结果、安全失败、不确定性和排除项。

## 8. 评审模型路线图

### 阶段 A：前沿模型评审

使用两个不同的强模型，温度设为 0，并强制输出 JSON。优势是开发快、理解复杂指令的能力强；风险包括供应商漂移、自我偏好、冗长偏好、共同盲区和成本。缓解措施包括固定模型快照、隐藏模型身份、独立调用、保存所有版本、用 Gold Set 校准并进行专家抽样。

### 阶段 B：混合分流

完成 Gold Set 校准后，将低风险、高置信度案例交给更便宜的模型或确定性规则。当小模型不确定、案例风险高、解析失败、评审分歧或可能存在关键错误时，升级到前沿模型。持续随机人工审计以发现漂移。

示例分流政策：

- 用确定性校验检查 schema 和可精确匹配的要求；
- 校准置信度不低于 0.85 且无安全标记时使用低成本评测器；
- 安全敏感或不确定案例使用两个前沿评审；
- 未解决的关键错误、实质分歧和随机审计样本进入人工裁决。

### 阶段 C：可选蒸馏/开源评测器

只有在拥有足够规模、多样且经过裁决的标签，以及稳定 rubric 后才训练。训练集、校准集和测试集必须按“案例家族”隔离，防止近重复泄漏。评估应覆盖校准性、子群体误差、关键错误召回率、分布漂移和鲁棒性，而不仅是与教师分数的相关性。蒸馏模型不能只用自己的教师模型作为唯一评价标准。

进入该阶段的触发因素可包括持续高调用量、隐私/本地部署要求、固定评测器权重的需求，以及计入工程和维护后仍可证明的总成本节省。

## 9. 成本控制

- 用 30–50 个案例开发，在约 100 个案例上校准，rubric 与提示词冻结后再跑全量。
- 按案例、回答、评审模型快照、rubric 和评审提示词的组合哈希缓存。
- 参考答案和关键要求保持简洁。
- 某个案例或局部 rubric 变化时，只重跑受影响项目。
- 安全相关案例采用两个评审；低风险回归检查可使用经校准的抽样。
- 记录 token、延迟、重试、解析失败和单次回答/评分成本。
- 将人工时间集中在 Gold Set、分歧、关键错误和随机审计。

不能通过单一且未校准的评审，或静默替换模型快照来降低成本。

## 10. 临床验证与 Gold Set

### 必需的临床专家流程

每个医疗案例至少由两位资质范围匹配的临床专家独立审核。审核内容包括场景真实性、参考答案、关键要求、关键错误及严重程度、适用评分维度、司法辖区、来源质量与生效日期。重大分歧由第三位合格裁决人解决。评审者不应看到候选模型身份。

### Gold Set 构建流程

1. 选择前先定义纳入和排除标准。
2. 按类别、风险、难度、语言和受保护情境切片抽样。
3. 防止开发集与 Gold Set 之间存在近重复泄漏。
4. 获取独立的人工维度评分和关键错误标签。
5. 裁决分歧并记录理由。
6. 在裁决前测量一致性，并预先定义上线阈值。
7. 锁定案例、标签和哈希值，限制访问。
8. 按计划更新，或在指南发生实质变化时更新。

建议由临床负责人最终确认的预发布阈值：自动评审在 Gold Set 上对关键错误的敏感度至少 0.95；与裁决后人工维度评分的加权一致性至少 0.80；不存在未解决的 3 级错误标签争议。这些只是规划建议，不是已验证标准。

## 11. 治理、隐私与安全

- v0.1 只使用合成或合规去标识化内容；通过制度和自动扫描禁止 PHI。
- 在考虑真实数据前完成数据最小化、访问控制、保存期限、加密和审计日志。
- 记录利益冲突和评审者资质范围。
- 建立案例撤回流程，处理错误、过时或已泄漏的案例。
- 将候选回答视为潜在不安全内容，将评审理由视为不可信模型输出。
- 保护隐藏案例；对已泄漏案例进行轮换。
- 部署或发布前完成适用的法律、隐私、安全、监管和临床治理审查。

## 12. 报告要求

至少报告：

- 样本量及各类别覆盖；
- 绝对分数的均值/中位数与 bootstrap 置信区间；
- 通过率以及 2/3 级关键错误率；
- 各维度和类别分数；
- 人工复核率与评审分歧率；
- 被排除/隔离案例及原因；
- 候选与评审模型快照、提示词、rubric、数据集和代码版本；
- 延迟和成本（如有）；
- 限制与验证状态。

当置信区间存在明显重叠时，应避免宣称排名高低。严重安全失败不能被平均分掩盖。成对排名只能补充绝对评分，不能替代安全门槛。

## 13. 部署前 MVP 阶段

### 阶段 0：章程与控制（第 1 周）

明确预期用途、评测层、用户、排除项、风险分类、数据规则、临床负责人、决策权限和发布标准。v0.2 Alpha 从 `jurisdiction=global_core` 开始，本地司法辖区作为独立扩展包加入。输出：获批的基准章程和风险登记表。

### 阶段 1：规范与 30–50 案例 Alpha（第 2–3 周）

确定 taxonomy、评分锚点、schema、案例编写指南、来源政策和复核表单；由临床专家审核 Alpha 集。输出：rubric v0.2、已裁决 Alpha 案例和歧义问题清单。

### 阶段 2：技术 Alpha 与评审校准（第 3–5 周）

实现真实供应商适配器、schema 校验、重试、成本记录、匿名化和运行清单。比较两个前沿评审与人工标签，测试偏差和提示词敏感性。输出：校准报告与候选的冻结评审提示词。

### 阶段 3：300–500 案例 MVP 与 Gold Set（第 5–9 周）

编写并双重审核案例；按案例家族裁决和划分；锁定隐藏 Gold Set。输出：数据集 v0.9、Gold Set v0.1、数据说明书和标注一致性分析。

### 阶段 4：部署前验证（第 9–11 周）

运行候选模型，完成重复性、敏感性、bootstrap 区间、子群体与失效模式分析，以及安全、隐私和红队测试。输出：验证报告与 go/no-go 决策。

### 阶段 5：有限内部试点（第 12 周起）

仅用于内部模型选择。监控评审漂移、成本、指南更新和泄漏。只有 Gold Set 结果支持时才启用混合分流。

以上任何阶段都不自动授权临床部署。临床部署必须经过独立的产品安全与监管流程。

## 14. 扩展到金融与法律

继续使用案例、回答、评审、人工复核、分数、运行和版本 schema。替换领域 taxonomy、权威来源政策、专家资质、关键错误目录和必要的评分维度。金融可加入适当性、数值准确性、时效性和市场数据溯源；法律可加入司法辖区、法律效力层级、程序阶段、引证有效性和避免未经许可执业等维度。保留 0–4 分锚点与关键错误门控的基本思想，使跨行业流程一致，但不要假设不同领域总分可直接比较。

## 15. 待决事项

- 全球核心工作流边界，以及选择后续司法辖区扩展包的标准。
- 正式验证版本支持的语言。
- 人工一致性指标与发布阈值。
- 公共/私有案例比例与排行榜政策。
- 参考来源层级和指南更新频率。
- 类别权重依据患病/使用频率、风险，还是固定均衡样本。
- 供应商模型快照可用性及数据保留条款。
- 所有权、许可证和外部发布政策。
