# 数据契约与版本管理 v0.1 — 中文

规范的机器可读定义位于 `schemas/`。SQLite 将核心标识符存为列，并把完整记录存为 JSON，使字段可以演进而不必每次立即迁移数据库。

## 1. 实体关系

| 实体 | 用途 | 不可变身份 |
|---|---|---|
| 案例 | 提示词、参考答案、可观察要求、禁止错误、来源 | `case_id + case_version + content_hash` |
| 模型回答 | 候选输出与生成元数据 | `response_id`；关联精确案例与模型身份 |
| 评审输出 | 一次独立的结构化评价 | `judge_output_id`；关联回答、评审模型、提示词与 rubric |
| 聚合分数 | 确定性聚合与门控结果 | `response_id + 评分政策版本` |
| 人工复核 | 专家确认、覆盖、升级或排除 | `review_id`；永不覆盖原始输出 |
| 案例审核 | 数据集升级前对案例内容进行专家验证 | `case_review_id`；关联精确案例版本 |
| 成对结果 | 匿名 A/B 偏好 | 比较 ID、按顺序记录的回答 ID 与随机种子 |
| 基准运行 | 一次受控执行 | `run_id` 与可复现清单 |
| 版本清单 | 复现和解释运行所需的完整溯源 | 按内容寻址的发布产物 |

## 2. 案例契约

必需字段：稳定 ID、语义版本、生命周期状态、行业/类别、提示词、参考答案、关键要求、逐案例关键错误、适用维度和元数据。每个关键错误具有稳定 ID、1–3 级严重度和供复核者阅读的描述。`trigger_terms` 只用于 mock/测试；生产环境中的关键错误必须通过语义判断。

生产环境建议增加案例家族 ID、作者、独立审核人、司法辖区、指南/来源、生效日期、预期工作流、敏感标签和变更理由。

双语 Alpha 将 `language`、`metadata.case_family_id`、`metadata.benchmark_layer`、司法辖区、地区和翻译方式作为编写政策字段。全球核心发布案例要求每个案例族具有完整的 `en` 和 `zh-Hans` 变体，并使用 `jurisdiction=global_core`。案例族变体共享分类、难度、评测层、司法辖区、适用维度以及关键错误 ID/严重度，但文本必须独立审核。司法辖区扩展包使用明确的本地司法辖区，并在 `metadata.locale` 中记录带地区的值。

状态转换应受控：

```text
draft -> clinician_validated -> gold
  \-> withdrawn / quarantined（发布流程状态）
```

示例状态 `example_unvalidated` 不得自动转换。

## 3. 模型回答契约

回答必须保留精确的案例版本、候选供应商/模型/快照、候选提示词模板版本、请求参数、文本、结束原因、延迟、用量、时间戳，以及可选的原始输出引用。不能根据营销名称推断模型版本。如果供应商没有不可变快照，应保存其返回的模型字符串、请求日期、可用的端点修订号，并标记可复现性受限。

本地文件试运行使用 `schemas/candidate-prompt-exchange.schema.json` 与 `schemas/candidate-answer-exchange.schema.json`。题目导出采用字段白名单，仅包含指令、案例题目、语言、案例 ID/版本/哈希和提示词模板版本；不包含参考答案、关键要求、错误标签或审核意见。回答导入要求每个精确案例修订版恰有一条非空记录；模型身份在创建运行时统一提供。试运行尚未记录完整生产环境回答清单，也不会调用真实 API。见 `docs/CANDIDATE_PILOT_ZH.md`。

## 4. 评审输出契约

每个适用维度包括数值分、适用标记、简短理由和候选回答中的引用证据。输出另行列出已配置的关键错误 ID、置信度、总体理由和人工复核标记。生产环境应拒绝未知字段，防止提示词或 schema 漂移被静默接受。

解析/修复历史保存在最终评审负载之外。不得静默修复会改变含义的字段。可以允许一次受约束的格式修复；再次失败则按固定政策进入复核或重试。

## 5. 人工复核契约

记录匿名评审者 ID、角色、资质范围、利益冲突披露、rubric 版本、决定、分数、关键错误标签、书面说明和时间戳。人工复核采用追加记录，不能修改模型或评审原始输出。另设确定性解析流程选择权威标签并记录完整裁决链。

`human-review.schema.json` 用于审核模型回答；`case-review.schema.json` 则单独用于审核已编写案例的临床内容、语言等价性、方法和裁决。模型回答审核不能作为案例本身已验证的证据。

每项案例审核都绑定 `case_id + case_version + case_content_hash`。哈希是可审核案例内容的规范 UTF-8 JSON（键排序、紧凑分隔符、保留 Unicode）的全小写 SHA-256 摘要。升级流程产生的字段不计入哈希：顶层 `status`，以及 `metadata.clinician_validated`、`reviewer_ids`、`translation_method`、`translation_reviewer_id` 和 `change_rationale`。题目、参考行为、要求、错误政策、来源、范围、日期及其他实质字段仍受哈希保护。如果实质内容不一致，即使作者忘记提升案例版本，该审核也会被视为过期。纠错时应追加新记录，并可用 `supersedes_review_id` 指向旧记录；已完成记录不得覆盖。

## 6. 版本清单

每次真实运行必须记录：

- 基准、数据集、rubric、候选提示词和评审提示词版本；
- 每个候选与评审供应商、模型 ID、可用的不可变快照/修订；
- 解码参数、随机种子、超时、重试和结构化输出模式；
- 代码提交/发布版本、Python/环境指纹和 schema 版本；
- 案例内容哈希与来源指南生效日期；
- 创建时间与操作者/服务身份；
- 隐私模式与原始输出保存政策。

已完成的清单不得编辑。任何纠错都创建新运行，并链接被替代的运行。

创建运行时，脚手架会把当前有效的 `case_id + case_version + content_hash` 集合快照写入 `run_cases`。后续数据集导入可以改变当前有效集合，但不能静默改变已有运行。历史案例版本继续保存在案例表中以便审计。

## 7. 语义版本政策

- **Patch：** 已证明不改变预期行为或评分的错字/元数据修正。
- **Minor：** 新增案例、澄清参考答案/锚点，或增加向后兼容 schema 字段；分数可能变化，必须标注新版本。
- **Major：** taxonomy、权重、门控、预期用途或不兼容 schema 变化；不同 major 的分数不能直接比较。

案例版本与数据集版本独立推进。任何提示词、参考答案、关键要求或关键错误变更都创建新的案例版本与内容哈希。数据集发布是精确案例版本的不可变列表。

## 8. 可复现与审计规则

- 使用 UTC ISO-8601 时间戳。
- 提示词和参数按版本与内容哈希保存。
- 政策允许时，在访问控制下保存候选与评审原始输出。
- 记录重试和供应商请求 ID，但不记录密钥。
- 日志和 v0.1 案例不得包含 PHI/PII。
- 报告必须从不可变原始记录生成，并携带 run ID。
- 未完成或 schema 无效的运行应隔离，不得参与比较。

## 9. 扩展契约

新行业复用实体和版本契约，可以增加领域元数据与评分维度，但不得削弱运行溯源和关键错误追踪。除非有专门校准研究支持，否则禁止直接比较不同行业分数。
