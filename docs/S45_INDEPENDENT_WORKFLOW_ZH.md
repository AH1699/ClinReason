# S45：先保存模型回答，再分别评分

这一步要解决的实际问题是：不能因为一家供应商暂时无法处理请求，就让整个项目停下来。用户已同意按这个方向推进。我们另开 S45 开发试跑，原来的 S41 停止记录以及 S43、S44 诊断结果保持原样，不续用它们剩下的请求次数，也不把等待 xAI 回复作为继续开发的前提。

## 现在怎么跑

先让被测模型作答。每条有效回答立即写入本地，并绑定模型名称、题目版本、题目内容指纹、实际请求指纹和原始返回指纹。第二轮只接上该模型自己的第一轮原文。被测模型看不到参考答案、评分标签，也看不到尚未出现的后续病情。

作答阶段结束后，形成固定的 `answer-bank.json`。随后，评分模型分别完成自己的对照检查，再读取同一批已保存的回答评分。这样，即使一个评分模型出错，已经生成的回答仍然可用；以后换一个评分模型，也不需要重新向被测模型提问。

如果返回已经能核算费用，但内容或格式不合格，只关闭这个模型后续的任务。其他模型可以继续。若费用未知、请求中断，或达到共享支出停止线，则停止所有新的付费请求。已发生的失败不会自动重试，也不会当作临床能力零分。若原始回复已完整保存，只是最后写结果文件时中断，可以离线核验并恢复回答；恢复过程不发新请求。

代码放在 `scripts/independent_eval_s45.py`。以前已经冻结的 `benchmark/*.py`、S36 算分规则和 S41/S43/S44 文件都不改，避免把不同协议的结果混为一谈。

## 这次小试跑的范围

| 内容 | 本次安排 |
|---|---|
| 题目 | 现有条件判断型用药安全题 `HC-MT-MEDSAFE-013` |
| 语言 | 英文、简体中文，各两轮 |
| 被测模型 | Gemini 3.5 Flash-Lite、Gemini 3.8 Flash、MiniMax M3.1 Flash、MiniMax M3 |
| 评分模型 | Gemini 3.8 Flash；Grok 暂缓 |
| 作答请求 | 最多 16 次 |
| 对照检查 | 最多 36 次，沿用 L/M/N 三类机制的已编写对照回答 |
| 正式评价本次回答 | 对照通过后，最多 16 次分阶段评价 |
| 总请求数 | 最多 68 次，串行，不自动重试 |
| 支出规则 | 记录金额达到 5 美元后停止；最后一笔可能造成超出 |

这 5 美元是本次新试跑的小范围停止线，沿用用户已经接受的“允许最后一笔超出”规则，不是供应商保证的硬上限。我们没有替用户设置账户限额。Gemini 和 MiniMax 的金额依据 token 和公开价格估算，不等于账单；历史上尚未查清的费用也不会被清零。价格已按 2026 年 10 月 24 日的 [Google 定价页](https://ai.google.dev/gemini-api/docs/pricing)和 [MiniMax 定价页](https://platform.minimax.io/docs/pricing/overview)核对。

这道题关注药物背景如何改变对血糖和症状的解释，在看到本次模型回答之前选定。它的作用是检查流程，不代表完整临床能力。模型版本和生成参数沿用现有 S38 设置，输出上限仍为 8192；S44 的结果并不支持“去掉上限就能解决 xAI 拒绝请求”。本地环境文件中的默认模型名不会覆盖本次固定名单。

发送给供应商的内容限于公开合成题、作者编写的对照回答、模型可见回答和评分材料。西安原始病历、购买的源文件、留作后续确认的题目以及密钥都不放入评测提示。`store=false` 也不等于供应商完全不留存数据。

## 对照怎样算通过

每个评分模型单独检查：36 条全部有效；6 个危险回答全部识别到指定错误；6 组都满足“完整回答 > 部分回答 > 危险回答”；12 组重复分阶段判断至少 11 组一致；6 组部分回答的重复分差全部不超过 5 分。

这是本次新声明的单评分模型检查，不能说成原先 72 条、两个评分模型的检查已经通过。它检验的是相对于作者预设的稳定性，不能替代医生确认标签是否正确。

算分仍使用 S36 的规则：按要求完成度给分，首轮占 30%、更新轮占 70%，再执行关键错误的扣分或封顶。某个模型缺了回答或评分，对应格子仍保留在总分母中，不只算成功的部分。数据不足时显示分数区间，不给完整均分。不同评分模型的结果不混在一起。

Gemini 给 Gemini 作答评分可能存在偏好。因此，这次结果只用于开发，不能据此发布排名。用户希望普通模型约 80 分、较弱模型约 60–70 分、较强模型约 90 分，这个目标继续保留；我们不会为了贴近目标而调整已得到的分数。四个模型、一组双语题也不足以验证原六模型名单的平均水平。

## 本地怎样查看

```sh
python3 -m scripts.independent_eval_s45 plan
python3 -m scripts.independent_eval_s45 audit
python3 -m unittest tests.test_independent_eval_s45 -v
python3 -m scripts.independent_eval_s45 report --directory work/s45-runs/RUN_UUID
```

上述命令只检查或读取本地材料，不读密钥、不发请求。真正执行需要显式使用 `run`、新的运行编号，以及记录用户实际同意内容的说明。密钥只在内存中使用；原始返回保存在 Git 忽略的 `work/s45-runs/`。同一运行目录不能再用。授权说明是操作记录，不是自动验证用户同意的系统；不能靠换个编号就自行增加一轮测试。

以后追加另一位评分模型时，使用单独配置：关闭重新生成回答，固定原回答库路径和指纹，保留原模型、题目、语言的分母，声明新的评分模型及次数，然后另行冻结。新评分模型仍需完成自己的对照检查。

## 接下来根据什么决定扩大

先看小试跑是否完整、对照是否通过、是否仍有满分堆积，以及扣分是否落在实际漏掉的要求上。流程和对照都通过后，再准备原有九家庭、不同难度分层的开发面板及重复评分。与此同时，继续独立准备 Batch O 更复杂的新题和西安病历的本地时间线。专家临床和双语复核依然放到双方约定的后期。
